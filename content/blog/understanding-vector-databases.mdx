Vector databases have quietly become one of the most important pieces of infrastructure in modern AI systems. If you've built anything with embeddings — semantic search, RAG pipelines, recommendation engines — you've either used one or rolled your own approximation of one.

This post walks through how they work under the hood.

## What is a vector embedding?

An embedding is a numerical representation of data — text, images, audio — as a fixed-length array of floats. Models like `text-embedding-ada-002` or `sentence-transformers` convert a sentence into a 768 or 1536-dimensional vector where semantically similar inputs land close together in space.

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")

sentences = [
    "Machine learning is a subset of AI.",
    "Deep learning uses neural networks.",
    "Postgres is a relational database.",
]

embeddings = model.encode(sentences)
print(embeddings.shape)  # (3, 384)
```

The key insight: **similarity in meaning maps to proximity in vector space**. Two sentences about neural networks will have a higher cosine similarity score than one sentence about ML and one about databases.

## The naive approach — and why it breaks

The obvious implementation is a brute-force nearest-neighbor search: compute the distance between the query vector and every stored vector, then return the top-k closest.

```python
import numpy as np

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def brute_force_search(query, corpus, k=5):
    scores = [(i, cosine_similarity(query, vec)) for i, vec in enumerate(corpus)]
    return sorted(scores, key=lambda x: -x[1])[:k]
```

This works fine at 10,000 vectors. At 10 million vectors and 100ms latency requirements, it doesn't.

## How vector databases actually work — HNSW

Most production vector databases use **Hierarchical Navigable Small World (HNSW)** graphs as their index structure. The idea is to build a multi-layer graph where:

- The top layer is sparse — only a few "hub" nodes with long-range connections
- Lower layers are progressively denser
- Search starts at the top layer and greedily navigates toward the query vector, descending into finer layers

This gets approximate nearest neighbor (ANN) search down to `O(log n)` instead of `O(n)`, with recall typically above 95% in practice.

```python
import hnswlib

# Build index
index = hnswlib.Index(space="cosine", dim=384)
index.init_index(max_elements=100_000, ef_construction=200, M=16)
index.add_items(embeddings, ids=list(range(len(embeddings))))

# Query
index.set_ef(50)  # higher = more accurate, slower
labels, distances = index.knn_query(query_embedding, k=5)
```

## Choosing a vector database

| Database | Best for | Notes |
|---|---|---|
| Pinecone | Managed, zero ops | Fully hosted, generous free tier |
| Weaviate | Hybrid search | Combines vector + BM25 keyword search |
| pgvector | Already on Postgres | Great for smaller scale, no new infra |
| Chroma | Local dev / prototyping | Easiest to get started |
| Qdrant | High throughput | Written in Rust, very fast |

## When to use pgvector vs a dedicated store

If you're already running Postgres and your scale is under ~1M vectors with non-critical latency, `pgvector` is often the right call. You get transactions, joins, and no new system to operate.

```sql
-- Create a table with a vector column
CREATE TABLE documents (
  id SERIAL PRIMARY KEY,
  content TEXT,
  embedding VECTOR(384)
);

-- Find the 5 most similar documents
SELECT content, embedding <=> $1 AS distance
FROM documents
ORDER BY distance
LIMIT 5;
```

For anything requiring sub-10ms search at scale, a dedicated store with HNSW is worth the operational overhead.

## Wrapping up

Vector databases solve a specific problem: fast similarity search over dense numerical representations. Understanding the tradeoffs between exact vs. approximate search, and between specialized stores vs. extensions like pgvector, will save you from over-engineering early and under-engineering late.
